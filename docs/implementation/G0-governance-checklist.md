# G0 — Governance & Data Contract Checklist: BOB People Connector

> **วัตถุประสงค์ของเอกสาร:** ให้ HR และ Data Owner ทบทวนและอนุมัติ (G0) ก่อนเปิด People Connector ให้พนักงานใช้จริง
> **สำหรับ:** HR / Data Owner / ผู้บริหารที่ดูแลข้อมูลพนักงาน
> **สถานะโค้ด (ณ ปัจจุบัน):** pipeline สร้างเสร็จ + ทดสอบแล้ว (145/145 tests) แต่ **ยังไม่เปิดให้ใครใช้** — inert จนกว่าจะตั้ง `PEOPLE_ENABLED=1`
> อ้างอิงแผนหลัก: Notion "BOB People Connector — Flexible Conversation Plan" (§5 data contract, §8 guardrails, §12 decisions)

---

## 1. ขอบเขต — People Connector ทำอะไร / ไม่ทำอะไร

**ช่วยพนักงานหา:**
- คน/ทีม/หัวหน้า จากทะเบียนพนักงาน ("พี่โบ๊ทอยู่ทีมไหน", "ทีม Jubili มีใครบ้าง", "หัวหน้าของ X คือใคร")
- ผู้ดูแล/ผู้เชี่ยวชาญเรื่องหนึ่ง ๆ (ต้องมี tags — ดู §3)
- ร่างข้อความติดต่อ (ผู้ใช้ตรวจและส่งเอง)

**ไม่ทำเด็ดขาด (บังคับด้วยโค้ด — ดู §4):**
- ไม่ให้ข้อมูลส่วนตัว (เงินเดือน วันลา สุขภาพ ผลประเมิน)
- ไม่จัดอันดับ/ประเมิน/ทำนายการลาออกของบุคคล
- ไม่ให้รายชื่อพนักงานทั้งบริษัท (company-wide enumeration)
- ไม่ส่งข้อความหาใครอัตโนมัติ

---

## 2. แหล่งข้อมูล — 2 ชั้น

### 2.1 Directory layer — ✅ พร้อมแล้ว (ข้อมูล "For All")
มาจากทะเบียน **"BOG ทะเบียนพนักงาน For All.xlsx"** ที่ HR **เผยแพร่ให้พนักงานทุกคนอยู่แล้ว** ผ่าน Microsoft Graph → sync อัตโนมัติ
ฟิลด์ที่ใช้ (allowlist ตายตัว): ชื่อ-นามสกุล, ชื่อเล่น, email, org, sub-org/แผนก, ตำแหน่ง, function/ทีม, หัวหน้า (Supervisor), วันที่เริ่มงาน/อายุงาน

- [ ] **HR/Data Owner ยืนยัน:** BOB ตอบข้อมูล directory ข้างต้น *เกี่ยวกับเพื่อนร่วมงาน* ให้พนักงานได้ (เพราะเป็นข้อมูล For-All ที่เผยแพร่ภายในแล้ว)
- [ ] ยืนยันว่าแสดง **company email** เป็นค่าเริ่มต้นคู่กับ Teams ได้

### 2.2 Tags layer — 🔴 ต้องการ input จาก HR (นี่คือ G0 หลัก)
ต้องเพิ่ม **2 คอลัมน์** ในทะเบียน + กำหนดเจ้าของข้อมูล:

- [ ] **คอลัมน์ "ownership/product"** — ใครดูแลผลิตภัณฑ์/เรื่องอะไรอย่างเป็นทางการ (เช่น "Pojjaman", "ประกันกลุ่ม") → ป้อน `OWNER_LOOKUP`
- [ ] **คอลัมน์ "employment status"** — สถานะการจ้าง (เพื่อกันตอบข้อมูลคนที่ไม่ได้อยู่สถานะปกติ; ตอนนี้ตัด "ลาออก" ได้แล้วจาก section ในไฟล์ แต่ยังแยกละเอียดไม่ได้)
- [ ] ระบุ **Data Owner** ผู้รับรอง ownership tags และรอบการยืนยัน
- [ ] (Phase ถัดไป) expertise / open-to-discuss tags — ต้องเจ้าของ profile ยืนยันเอง ยังไม่ต้องอนุมัติตอนนี้

> จนกว่าคอลัมน์เหล่านี้จะพร้อม+อนุมัติ: คำถามแนว "ใครดูแล/เชี่ยวชาญ X" BOB จะตอบว่า *"กำลังจะเปิดเร็ว ๆ นี้"* — ส่วนหา คน/ทีม/หัวหน้า ใช้ได้เลย

## 4. สิ่งที่ระบบ "บังคับด้วยโค้ด" อยู่แล้ว (ให้ความมั่นใจ — ทดสอบผ่าน 100%)

- [x] **Policy gate ปฏิเสธหัวข้อต้องห้ามก่อนเสมอ** (เงินเดือน/ลา/สุขภาพ/ประเมิน/จัดอันดับ/gossip/ทำนายลาออก/รายชื่อทั้งบริษัท) — 22 คำถามต้องห้าม + 16 prompt-injection ถูกปฏิเสธ 100%
- [x] **fail-closed** — คลุมเครือ/ไม่มั่นใจ → ถามกลับ ไม่เดา
- [x] **ไม่ปล่อยชื่อ/อีเมลเกินจริง** — ตัวตรวจ deterministic ทิ้งคำตอบ AI ที่แต่งชื่อ/อีเมลที่ไม่มีในผลค้นหา แล้วใช้ข้อความ template แทน
- [x] **ไม่มีรหัสเทคนิคหลุด** — ระบบไม่เคยนำเข้ารหัส Payroll/employee ID เลย
- [x] **Audit เก็บเท่าที่จำเป็น** — เก็บแค่ {ประเภทคำถาม, ผลนโยบาย, จำนวนผล, เวลา} ไม่เก็บข้อความคำถามที่ถูกปฏิเสธ
- [x] **ไม่ส่งข้อความอัตโนมัติ** — โมดูลร่างข้อความไม่ต่อกับตัวส่งใด ๆ (มี test ยืนยัน)

## 5. Rollout — เปิดทีละขั้น (แผน §10)

- [ ] **ขั้น 0 — shadow (แอดมินเท่านั้น):** เปิด `/people` ให้แอดมินทดสอบด้วยคำถามจริง วัดความแม่น/ชื่อหลุด — **ไม่ต้องรอ tags** ทำได้ทันทีหลังอนุมัติ §2.1
- [ ] **ขั้น 1 — pilot:** 10–20 คน / 2 สัปดาห์ (หลังเพิ่ม ownership tags)
- [ ] **ขั้น 2 — controlled rollout** → review → scale
- [ ] เกณฑ์ผ่านแต่ละขั้น: ไม่มีข้อมูลส่วนตัว/ชื่อหลุด, no-result rate + wrong-match ต่ำ, feedback เชิงบวก
